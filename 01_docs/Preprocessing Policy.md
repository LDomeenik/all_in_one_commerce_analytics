
# 전처리 정책서

```
본 문서는 업로드된 이커머스 데이터를
분석 가능한 형태로 표준화하고 정제하기 위한 전처리 기준을 정의하는 것을 목적으로 합니다.

본 프로젝트의 전처리는 단순 데이터 정제를 넘어,
컬럼 표준화, 데이터 타입 변환, 정합성 검증, 분석 가능 여부 진단까지 
포함하는 구조로 설계합니다.

전처리 과정은 Raw → Staging → Data Mart 흐름 중
Staging Layer를 중심으로 수행되며,
이후 분석 모듈이 안정적으로 동작할 수 있는 기준 데이터를 생성하는 역할을 수행합니다.

본 문서는 다음 범위를 대상으로 적용됩니다.

- CSV 및 Excel 형태로 업로드된 이커머스 데이터
- 주문, 고객, 상품, 결제, 배송 등 일반적인 Order Domain 데이터
- 컬럼 자동 매핑 이후의 표준 컬럼 데이터

적용 범위들을 대상으로 다음과 같은 작업이 이루어집니다.

- 데이터 타입 표준화 및 문자열 정규화
- 결측치 처리 및 데이터 정합성 검증
- 중복 데이터 및 이상 데이터 처리
- 분석 가능 여부 진단을 위한 데이터 품질 검증
- Raw → Staging → Data Mart 전 단계 중 전처리 기준 정의
  
본 프로젝트의 전처리는 원본 데이터 보존을 기본 원칙으로 하며,
Raw Layer의 데이터는 수정하지 않습니다.

또한 전처리 과정에서 발생하는 데이터 오류 및 품질 문제는
가능한 한 삭제보다 상태값(Flag) 기반으로 관리하여,
데이터 추적 가능성과 분석 신뢰성을 유지하도록 설계합니다.

※ 본 문서는 MVP 기준으로 작성되었으며, 향후 분석 모듈 확장 및 데이터 구조 변경에 따라 
  지속적으로 수정 및 보완될 수 있습니다.  
```

## 1. 전처리 설계 원칙

```
본 프로젝트의 전처리는 단순 데이터 정제가 아니라,
다양한 이커머스 데이터를 분석 가능한 형태로 안정적으로 변환하기 위한 
표준화 과정으로 정의합니다.

전처리 과정은 이후 Data Mart 구성 및 분석 모듈 실행의 기반이 되므로,
데이터 품질과 구조 일관성을 유지할 수 있도록 다음 원칙을 기준으로 설계합니다.

- 원본 데이터 보존
- 표준 컬럼 기반 처리
- 분석 중심 전처리
- Flag 기반 데이터 관리
- 자동화 우선 설계
- 분석 가능 여부와 데이터 삭제의 분리
- Layer 역할 분리
- 확장 가능 구조 유지
```

- **원본 데이터 보존**
	- Raw Layer의 데이터는 수정하거나 삭제하지 않음
	- 모든 전처리는 Staging Layer에서 수행
	- 원본 데이터 재처리 및 추적 가능성을 유지

- **표준 컬럼 기반 처리**
	- 컬럼 자동 매핑 이후의 표준 컬럼 구조를 기준으로 전처리 수행
	- 원본 컬럼명이 아닌 표준 컬럼 기준으로 데이터 처리 로직 관리
	- 전처리와 데이터 구조를 분리하여 유지보수성 확보

- **분석 중심 전처리**
	- 단순 데이터 정제보다 분석 가능 상태 확보를 우선 목표로 설정
	- KPI, 코호트, RFM, 상품 분석 등 주요 분석 수행 기준으로 전처리 정책 정의
	- 분석 로직에서 반복되는 데이터 처리 작업 최소화

- **Flag 기반 데이터 관리**
	- 오류 데이터는 즉시 삭제하지 않고 상태값(Flag) 기반으로 관리
	- 결측치, 이상치, 날짜 오류, 정합성 오류 등을 별도 상태 컬럼으로 기록
	- 데이터 품질 문제를 추적 가능하도록 설계

- **자동화 우선 설계**
	- 반복적인 데이터 정제 작업을 자동 수행 가능한 구조로 설계
	- 데이터 타입 변환, 문자열 정규화, 날짜 처리 등을 자동화
	- 사용자 개입 없이 기본 분석이 가능하도록 구성

- **분석 가능 여부와 데이터 삭제의 분리**
	- 분석 불가능 데이터와 제거 대상 데이터를 동일하게 처리하지 않음
	- 특정 분석에 사용 불가능한 데이터는 제외 상태로 관리
	- 데이터 손실 최소화를 우선 원칙으로 적용

- **Layer 역할 분리**
	- Raw Layer:
		- 원본 데이터 저장
	- Staging Layer:
		- 표준화 및 전처리 수행
	- Data Mart Layer:
		- 분석 목적 기준 데이터 구성
	- Analytics Layer:
		- 분석 모듈 실행 및 결과 생성

- **확장 가능 구조 유지**
	- 신규 분석 모듈 및 신규 표준 컬럼 추가를 고려한 구조 유지
	- 특정 플랫폼 또는 특정 데이터 구조에 종속되지 않도록 설계
	- 향후 Event, Funnel, LTV 등 확장 분석 지원 가능하도록 구성

## 2. 전처리 전체 Flow

```
본 프로젝트의 전처리는 업로드된 원본 데이터를
분석 가능한 표준 데이터 구조로 변환하기 위한 단계별 처리 과정으로 구성됩니다.

전처리 과정은 컬럼 자동 매핑 이후 수행되며,
데이터 타입 표준화, 문자열 정규화, 결측치 처리, 
데이터 정합성 검증, 분석 가능 여부 진단 등을 포함합니다.

전체 전처리 흐름은 다음과 같습니다.

Raw Data 적재
→ 컬럼 자동 매핑 결과 적용
→ 컬럼 타입 표준화
→ 문자열 정규화
→ 결측치 처리
→ 데이터 정합성 검증
→ 이상 데이터 및 중복 데이터 처리
```


- **Raw Data 적재**
	- 사용자가 업로드한 원본 데이터를 그대로 저장
	- 원본 데이터 수정 없이 Raw Layer에 보관
	- 파일 정보 및 업로드 메타데이터 기록 가능

- **컬럼 자동 매핑 결과 적용**
	- 컬럼 매핑 정책서를 기준으로 원본 컬럼을 표준 컬럼으로 변환
	- 사용자 검수(Human Review) 결과 반영
	- 이후 전처리는 표준 컬럼 기준으로 수행

- **컬럼 타입 표준화**
	- 문자열, 숫자, 날짜 타입을 표준 데이터 타입으로 변환
	- 날짜 문자열 → DATE/DATETIME 변환
	- 금액 및 수량 컬럼 → NUMERIC 변환
	- 변환 실패 여부는 상태값으로 기록

- **문자열 정규화**
	- 공백 제거 및 대소문자 통일
	- 특수문자 및 불필요 문자 처리
	- 상태값(order_status 등) 표준화 수행
	- 문자열 비교 가능한 형태로 변환

- **결측치 처리**
	- 필수 컬럼과 선택 컬럼을 구분하여 처리
	- 분석 수행 가능 여부 기준으로 결측 상태 관리
	- 자동 보정 가능한 경우 기본값 또는 파생값 생성 가능
	- 결측 여부는 별도 Flag로 기록 가능

- **데이터 정합성 검증**
	- 날짜 순서 검증
		- order_date ≤ delivered_date
	- 금액 정합성 검증
		- revenue ≈ quantity × unit_price
	- ID 및 Key 중복 여부 검증
	- 상태값(domain) 유효성 검증

- **이상 데이터 및 중복 데이터 처리**
	- 중복 row 탐지
	- 비정상 수량 및 금액 탐지
	- 음수 금액 및 미래 날짜 검증
	- 이상 데이터 제거보다 상태 관리 우선 적용

## 3. 컬럼 타입 표준화 정책

```
컬럼 타입 표준화는 다양한 형태의 원본 데이터를
분석 가능한 일관된 데이터 타입으로 변환하기 위한 전처리 단계입니다.

이커머스 데이터는 플랫폼 및 기업마다 서로 다른 타입 구조를 가지며,
동일 의미의 데이터라도 문자열, 숫자, 날짜 형태가 포함되어 존재할 수 있습니다.

본 프로젝트는 표준 컬럼 기준으로 데이터 타입을 통일하여
이후 Data Mart 구성 및 분석 모듈 실행 시
추가 타입 변환 없이 안정적으로 처리할 수 있도록 설계합니다.

데이터 타입 변환은 Staging Layer에서 수행하며,
변환 실패 데이터는 삭제하지 않고 상태값(Flag) 기반으로 관리합니다.
```

### 3.1 기본 타입 표준

| 표준 컬럼 유형   | 표준 타입           | 예시                          |
| :--------- | --------------- | --------------------------- |
| ID 계열      | STRING          | `order_id`, `customer_id`   |
| 날짜 계열      | DATE / DATETIME | `order_date`                |
| 금액 계열      | NUMERIC         | `revenue`, `payment_amount` |
| 수량 계열      | INTEGER         | `quantity`                  |
| 상태값 계열     | STRING          | `order_status`              |
| Boolean 계열 | BOOLEAN         | `is_delayed`                |


### 3.2 타입 변환 기준

| 원본 형태          | 변환 대상         | 처리 방식             |
| :------------- | ------------- | ----------------- |
| 문자열 숫자         | NUMERIC       | 쉼표 및 통화기호 제거 후 변환 |
| 문자열 날짜         | DATE/DATETIME | 표준 날짜 포멧으로 변환     |
| 소수 포함 숫자       | NUMERIC       | Decimal 유지        |
| TRUE/FALSE 문자열 | BOOLEAN       | Boolean 변환        |
| 공백 문자열         | NULL          | NULL 처리           |


### 3.3 날짜 타입 처리 기준

- 날짜 문자열은 가능한 한 DATE 또는 DATETIME 타입으로 변환

- 지원 예시:
	- `2024-01-01`
	- `2024/01/01`
	- `2024-01-01 13:00:00`

- 날짜 변환 실패 시:
	- 원본 값 유지 가능
	- `is_invalid_date = TRUE` 상태 기록 가능

- 타임존 정보는 MVP 단계에서는 기본 미지원

- 표준 시간 기준은 UTC 또는 시스템 기본 시간 사용 가능


### 3.4 금액 및 수치 데이터 처리 기준

- 쉼표(`,`) 제거 후 숫자 변환 수행
	- 예:
		- `"35,000"` → `35000`

- 통화 기호 제거 가능
	- 예:
		- `"₩35,000` → `35000`

- 음수 금액 허용 여부는 컬럼 기준으로 관리
	- 환불 / 취소 데이터는 음수 허용 가능

- 변환 실패 데이터는 NULL 처리 또는 오류 상태 관리


### 3.5 문자열 타입 처리 기준

- 모든 문자열 컬럼은 UTF-8 기준으로 처리

- 문자열 앞뒤 공백 제거(TRIM)

- 비정상 공백 및 제어 문자 제거 가능

- 상태값(`order_status` 등)은 별도 표준화 규칙 적용 가능


### 3.6 타입 변환 실패 처리 정책

| 상황            | 처리 방식                |
| :------------ | -------------------- |
| 숫자 변환 실패      | NULL 처리 → 상태 Flag 기록 |
| 날짜 변환 실패      | 원본 유지 또는 NULL 처리     |
| BOOLEAN 변환 실패 | NULL 처리              |
| 필수 컬럼 변환 실패   | 분석 가능 여부 진단 대상 포함    |

- 변환 실패 데이터는 즉시 삭제하지 않음
- 오류 여부를 추적 가능한 상태값으로 관리
- 상태값 예시:
	- `is_invalid_numeric`
	- `is_invalid_date`
	- `is_invalid_boolean`


### 3.7 타입 표준화 원칙

- 원본 타입보다 분석 가능 타입을 우선 적용

- 모든 분석 모듈은 표준 타입 기준으로 동작

- 타입 변환 로직은 표준 컬럼 기준으로 관리

- 타입 오류는 삭제보다 추적 가능성 확보를 우선 적용

- 이후 Data Mart 및 Analytics 단계에서는 추가 타입 변환 최소화

## 4. 결측치 처리 정책

```
결측치 처리는 업로드된 데이터 내 NULL 값 또는 비어 있는 데이터를
분석 가능한 상태로 관리하기 위한 전처리 기준입니다.

이커머스 데이터는 플랫폼 및 데이터 구조에 따라
일부 컬럼이 존재하지 않거나 값이 누락된 경우가 빈번하게 발생합니다.

본 프로젝트는 모든 결측치를 일괄 제거하는 방식이 아니라,
컬럼의 역할과 분석 목적을 기준으로 결측치를 관리하는 것을 원칙으로 합니다.

또한 결측 데이터는 가능한 한 삭제보다 상태값(Flag) 기반으로 관리하여,
데이터 손실을 최소화하고 분석 가능 범위를 유지하도록 설계합니다.
```

### 4.1 결측치 분류 기준  
  
| 구분         | 설명                          |
| ---------- | --------------------------- |
| 필수 컬럼 결측   | 핵심 분석 수행 불가능 가능성이 있는 결측     |
| 선택 컬럼 결측   | 일부 분석 기능만 제한되는 결측           |
| 구조적 결측     | 원본 데이터 구조상 존재하지 않는 컬럼       |
| 처리 중 생성 결측 | 타입 변환 또는 정합성 검증 과정에서 발생한 결측 |
  
  
### 4.2 필수 컬럼 결측 처리 정책  
  
- 핵심 표준 컬럼은 필수 컬럼으로 관리
	- 예시:
		- `order_id`
		- `order_date`
		- `customer_id`
		- `revenue`

- 필수 컬럼 결측 시:
	- row 즉시 삭제하지 않음
	- 분석 제외 상태로 관리 가능
	- 분석 가능 여부 진단 대상 포함

| 컬럼            | 기본 처리                 |
| ------------- | --------------------- |
| `order_id`    | 중복 및 식별 불가 → 분석 제외 가능 |
| `order_date`  | 시계열 분석 제외             |
| `customer_id` | 고객 분석 제외              |
| `revenue`     | 매출 KPI 제외             |
  

### 4.3 선택 컬럼 결측 처리 정책
  
- 선택 컬럼 결측은 기본적으로 허용

- 해당 분석 기능만 제한 가능
	- 예시:
		- `product_category`
		- `payment_method`
		- `delivered_date`
  
| 컬럼 결측               | 영향            |
| ------------------- | ------------- |
| product_category 없음 | 카테고리 분석 제한    |
| payment_method 없음   | 결제 분석 제한      |
| delivered_date 없음   | 배송 리드타임 분석 제한 |
  

### 4.4 자동 보정 정책

```
일부 결측치는 기존 데이터 기반으로 자동 보정 가능하며,
자동 보정 여부는 컬럼 특성과 데이터 신뢰도를 기준으로 결정합니다.
```

- **자동 생성 가능 예시:**
	- `delivery_days`
		- = `delivered_date` - `shipped_date`
	- `year_month`
		- = `order_date` 기반 생성
	- `item_revenue`
		- = `quantity` * `unit_price`

- **자동 보정 시:**
	- 생성 여부 기록 가능
	- 원본 값과 구분 가능하도록 관리


### 4.5 문자열 결측 처리 기준

| 원본 값     | 처리 결과   |
| :------- | ------- |
| `""`     | NULL    |
| `" "`    | NULL    |
| `"N/A"`  | NULL 가능 |
| `"null"` | NULL 가능 |
| `"None"` | NULL 가능 |

- 문자열 정규화 이후 결측 여부 판단 수행
- 대소문자 차이는 무시 가능


### 4.6 결측 상태 관리 정책

- 결측 데이터는 상태값(Flag) 기반으로 관리 가능

- 예시 Flag:
	- `is_missing_order_date`
	- `is_missing_customer_id`
	- `is_missing_revenue`

- 상태값 활용 목적:
	- 분석 제외 기준 관리
	- 데이터 품질 추적
	- QC 리포트 생성
	- 사용자 알림 제공


### 4.7 분석 가능 여부와 결측 처리

| 상태    | 설명             |
| :---- | -------------- |
| 실행 가능 | 핵심 필수 컬럼 존재    |
| 제한 실행 | 일부 선택 컬럼 결측    |
| 실행 불가 | 핵심 필수 컬럼 다수 결측 |

- 결측 데이터가 존재 자체가 즉시 실패를 의미하지는 않음
- 분석 목적 기준으로 실행 가능 여부 판단


### 4.8 결측치 처리 원칙

- 삭제보다 분석 가능 범위 유지 우선

- 필수 컬럼과 선택 컬럼을 구분하여 처리

- 자동 보정 가능한 경우 최소 범위 내 생성 허용

- 결측 여부를 추적 가능한 상태값으로 관리

- 분석 로직 내부에서 반복 결측 처리하지 않도록 전처리 단계에서 관리

## 5. 데이터 정합성 검증 정책

```
데이터 정합성 검증은 전처리된 데이터가 실제 이커머스 비즈니스 규칙 및
분석 기준에 맞는 구조를 가지는지 확인하기 위한 검증 단계입니다.

본 프로젝트의 정합성 검증은 단순 형식 검사만 수행하는 것이 아니라,
주문, 결제, 상품, 배송 간의 관계 및 도메인 규칙을 기반으로
분석 가능한 데이터 상태를 판단하는 것을 목적으로 합니다.

정합성 검증은 Staging Layer에서 수행되며,
검증 실패 데이터는 즉시 삭제하지 않고 상태값(Flag) 기반으로 관리합니다.

검증 대상 범위는 다음과 같습니다.

- 주문 데이터 (Order)
- 주문 상품 데이터 (Order Item)
- 고객 데이터 (Customer)
- 결제 데이터 (Payment)
- 배송 데이터 (Logistics)
- Derived 컬럼 및 파생 계산값
```

### 5.1 가본 검증 항목

| 검증 항목   | 설명                |
| :------ | ----------------- |
| ID 정합성  | 식별자 중복 및 NULL 여부  |
| 날짜 정합성  | 날짜 순서 및 미래 날짜 검증  |
| 금액 정합성  | 매출 및 결제 금액 검증     |
| 수량 정합성  | 음수 및 비정상 수량 검증    |
| 상태값 정합성 | 허용 상태값 여부 검증      |
| 관계 정합성  | 테이블 간 연결 가능 여부 검증 |


### 5.2 ID 정합성 검증

- 주요 식별자는 중복되지 않아야 함

- 필수 ID 컬럼은 NULL 불가 기준 적용 가능

| 컬럼            | 검증 기준            |
| :------------ | ---------------- |
| `order_id`    | 중복 불가            |
| `customer_id` | NULL 비율 검증       |
| `product_id`  | 상품 분석 시 존재 여부 검증 |

- 중복 발생 시:
	- 즉시 삭제하지 않음
	- 중복 상태 Flag 기록 가능

- 예시 Flag:
	- `is_duplicated_order_id`
	- `is_invalid_customer_id`


### 5.3 날짜 정합성 검증

| 검증 규칙                             | 설명             |
| :-------------------------------- | -------------- |
| `order_date` ≤ `shipped_date`     | 주문 이후 출고       |
| `shipped_date` ≤ `delivered_date` | 출고 이후 배송 완료    |
| `order_date` ≤ `delivered_date`   | 주문 이후 배송 완료    |
| 미래 날짜 여부                          | 현재 시점 이후 날짜 검증 |

- 날짜 역전 데이터는 오류 상태 관리 가능
- 일부 데이터셋은 배송 데이터 부재 가능
- 배송 데이터 미존재는 오류로 처리하지 않음

- 예시 Flag:
	- `is_invalid_flow`
	- `is_future_date`


### 5.4 금액 정합성 검증

| 검증 규칙                                      | 설명           |
| :----------------------------------------- | ------------ |
| `revenue` ≥ 0                              | 기본 매출 금액 검증  |
| `quantity` * `unit_price` = `item_revenue` | 주문 상품 금액 검증  |
| Σ `payment_amount` ≈ `revenue`             | 주문-결제 정합성 검증 |

- 환불 및 취소 데이터는 음수 허용 가능
- 오차 허용 범위 적용 가능
- 일부 플랫폼은 배송비 포함 여부가 다를 수 있음

- 예시 Flag:
	- `is_invalid_revenue`
	- `is_payment_mismatch`


### 5.5 수량 및 값 범위 검증

| 검증 항목                  | 기준          |
| :--------------------- | ----------- |
| `quantity`             | 0 이하 여부     |
| `shipping_fee`         | 음수 여부       |
| `payment_installments` | 비정상 할부 개월 수 |
| `delivery_days`        | 음수 여부       |

- 비정상 값은 제거보다 상태 기록 우선
- 플랫폼별 예외 허용 가능


### 5.6 상태값 검증

```
상태값 컬럼은 사전에 정의된 허용 값 집합을 기준으로 검증합니다.
```

- 예시:
	- `order_status`
		- delivered
		- canceled
		- shipped
		- pending

- 허용되지 않은 상태값 발견 시:
	- `unknown` 상태로 치환 가능
	- 또는 오류 Flag 기록 가능

- 예시 Flag:
	- `is_invalid_order_status`


### 5.7 관계 정합성 검증

- 다중 테이블 입력 시 테이블 간 연결 가능 여부 검증
- JOIN Key 존재 여부 확인

| 관계                   | 검증 기준                  |
| :------------------- | ---------------------- |
| Orders ↔ Customers   | `customer_id` 연결 가능 여부 |
| Orders ↔ Payments    | `order_id` 연결 가능 여부    |
| Orders ↔ Order Items | `order_id` 연결 가능 여부    |

- orphan 데이터 탐지 가능
- 관계 단절 데이터는 상태 관리 가능

- 예시 Flag:
	- `is_orphan_payment`
	- `is_orphan_order_item`


### 5.8 정합성 검증 실패 처리 정책

| 상태       | 처리 방식       |
| :------- | ----------- |
| 경미한 오류   | 상태값 기록 후 유지 |
| 분석 영향 적음 | 제한 분석 허용    |
| 핵심 구조 오류 | 분석 제외 가능    |

- 검증 실패 데이터 즉시 삭제 금지
- QC 및 사용자 검토 가능 상태 유지
- 분석 가능 여부 진단 단계와 연계


### 5.9 정합성 검증 원칙

- 분석 가능 데이터 유지 우선

- 삭제보다 상태 기반 관리 우선

- 도메인 규칙 기반 검증 수행

- 단일 컬럼이 아닌 데이터 관계 기준 검증 수행

- 이후 분석 모듈에서 반복 검증 최소화

## 6. 이상 데이터 및 중복 데이터 처리 정책

```
이상 데이터 및 중복 데이터는 분석 결과 왜곡 및 KPI 오류를 유발할 수 있으므로
전처리 단계에서 탐지 및 관리가 필요합니다.

그러나 이커머스 데이터에서는 실제 비즈니스 상황에 의해
일반적인 범위를 벗어나는 데이터가 존재할 수 있으므로,
본 프로젝트에서는 단순 제거 방식이 아닌
분석 목적 기반의 상태 관리 방식을 우선 적용합니다.

또한 중복 데이터 역시 단순 row 중복과 비즈니스적으로 허용 가능한 중복을 구분하여 처리합니다.
```

### 6.1 이상 데이터 정의 기준

| 유형     | 설명             |
| :----- | -------------- |
| 범위 이상치 | 일반 범위를 벗어난 값   |
| 논리 이상치 | 비즈니스 규칙 위반 값   |
| 구조 이상치 | 데이터 구조상 비정상 상태 |
| 통계 이상치 | 분포 기준 극단값      |

### 6.2 범위 이상치 처리 정책

| 컬럼              | 예시 검증        |
| :-------------- | ------------ |
| `revenue`       | 비정상 고액/음수 매출 |
| `quantity`      | 과도한 주문 수량    |
| `shipping_fee`  | 비정상 배송비      |
| `delivery_days` | 과도한 배송 기간    |

- 기본적으로 자동 삭제하지 않음
- 분석 왜곡 가능성이 높은 경우 상태값 기록
- 플랫폼 특성에 따라 허용 범위 조정 가능

- 예시 Flag:
	- `is_outlier_revenue`
	- `is_outlier_quantity`


### 6.3 논리 이상치 처리 정책

```
논리 이상치는 데이터 타입은 정상이나, 실제 비즈니스 흐름상 발생하기 어려운 데이터를 의미합니다.
```

- 예시:
	- 배송일 < 주문일
	- `quantity` = 0
	- `payment_amount` < 0
	- `delivery_days` < 0

- 논리 이상치는 분석 영향도가 높으므로 별도 관리
- 핵심 분석 제외 대상이 될 수 있음

- 예시 Flag:
	- `is_invalid_business_logic`
	- `is_negative_delivery_days`


### 6.4 통계 이상치 처리 정책

- IQR, Z-score 등 통계 기반 이상치 탐지 가능
- MVP 단계에서는 자동 제거보다 탐지 중심 적용
- 분석 모듈별 추가 처리 가능

- 예시:
	- 극단적 고액 주문
	- 극단적 재구매 고객
	- 비정상 대량 주문

- 이상치 제거 여부는 분석 목적 기준으로 결정
- KPI 왜곡 가능성 모니터링 목적 활용 가능


### 6.5 중복 데이터 처리 정책

| 유형      | 설명             |
| :------ | -------------- |
| 완전 중복   | 모든 컬럼이 동일      |
| PK 중복   | 동일 식별자 중복      |
| 비즈니스 중복 | 실질적으로 동일 주문    |
| 허용 중복   | 정상적인 다중 row 구조 |

- **완전 중복**
	- 모든 컬럼 값 동일
	- 제거 후보 가능
	- 원본 보존 원칙에 따라 상태 관리 우선 가능
	- 예시 Flag:
		- `is_full_duplicate`

- **PK 중복**
	- 예시
		- 동일 `order_id`
		- 동일 (`order_id`, `order_item_id`)
	- 처리 기준:
		- Order Grain:
			- 동일 `order_id` 중복 여부 검증
		- Order Item Grain:
			- 복합 Key 기준 검증
	- 예시 Flag:
		- `is_duplicated_order_id`
		- `is_duplicated_order_item`

- **허용 가능한 중복**
	- 예시:
		- 하나의 주문에 여러 상품 존재
		- 하나의 주문에 여러 결제 존재
		- 하나의 주문에 여러 배송 이벤트 존재
	- Grain 기준으로 정상 중복 여부 판단
	- 단순 row 수 기준으로 중복 판단하지 않음


### 6.6 이상 데이터 처리 방식

| 상태       | 처리 방식      |
| :------- | ---------- |
| 분석 영향 적음 | 유지 + 상태 기록 |
| 분석 왜곡 가능 | 제한 분석 대상   |
| 핵심 구조 오류 | 분석 제외 가능   |

- 자동 삭제 최소화
- 상태값 기반 추적 우선
- QC 리포트 생성 가능


### 6.7 이상 데이터 및 중복 처리 원칙

- 삭제보다 추적 가능성 확보 우선

- Grain 기준으로 중복 여부 판단

- 비즈니스 규칙 기반 이상치 우선 검증

- 자동 제거는 최소 범위로 제한

- 분석 목적에 따라 후속 단계에서 추가 처리 가능하도록 설계
